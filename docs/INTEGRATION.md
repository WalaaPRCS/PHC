# تكامل الأنظمة

## النسخة والهوية

- بادئة الواجهة: `/api/v1`.
- استخدم UUID الداخلي عند توفره، أو `patient_number` الثابت للملف السريري. لا تستخدم رقم الهوية كمعرّف تكاملي.
- أرسل `sourceSystem`, `entityType`, `localId`, `externalId`, و`externalVersion` عند ربط سجل خارجي. يسمح ذلك بمزامنة التحديثات ومنع تكرار السجل.
- كل استجابة API تتضمن `requestId` عند توفره لتتبع الأخطاء.

## مسارات حالية

| المسار | الاستخدام |
| --- | --- |
| `GET /api/v1/health` | حالة الخدمة واتصال PostgreSQL |
| `POST /api/v1/auth/login` | دخول مستخدم بشري باسم مستخدم وكلمة مرور |
| `POST /api/v1/integrations/clients` | إنشاء اعتماد مستقل لنظام متكامل ونطاقاته (مدير النظام) |
| `GET /api/v1/integrations/clients` / `POST /api/v1/integrations/clients/{clientId}/revoke` | عرض الاعتمادات أو إلغاء عميل ورموزه (مدير النظام) |
| `POST /api/v1/integrations/token` | إصدار رمز Bearer قصير العمر لعميل تكامل معتمد |
| `GET /api/v1/auth/session` / `POST /api/v1/auth/logout` | الجلسة الحالية وإنهاؤها |
| `GET /api/v1/state` | بيانات الشاشات المسموح بها وفق الدور والعيادة |
| `PUT /api/v1/records/{resource}` | حفظ مجموعة سجلات مورد؛ كتابة محكومة بالدور والنطاق |
| `GET /api/v1/patients/lookup?nationalId=...` | بحث مصرح برقم الهوية وإرجاع ملف موحد وآخر زيارة |
| `POST /api/v1/pharmacy/dispense` | صرف دواء متعدد الأصناف ضمن معاملة ذرية واحدة |
| `GET/POST /api/v1/interop/identity-map` | ربط المعرّفات الخارجية بجلسة إدارية أو نطاقات `identity-map:read` و`identity-map:write` |
| `GET/POST /api/v1/users` | إدارة الحسابات (مدير النظام فقط) |

## ربط المعرّفات

مثال طلب مدير النظام لإضافة مرجع من نظام آخر:

```json
{
  "sourceSystem": "legacy-phc",
  "sourceName": "نظام العيادات السابق",
  "entityType": "patient",
  "localId": "b26b772c-3f08-4a99-a4c1-000000000001",
  "externalId": "OLD-REC-39201",
  "externalVersion": "7"
}
```

أرسله إلى `POST /api/v1/interop/identity-map` داخل جلسة مدير النظام. يفرض الجدول عدم تكرار المعرّف المحلي أو الخارجي ضمن النظام المصدر ونوع الكيان.

## الوصول من خدمة إلى خدمة

ينشئ مدير النظام لكل نظام متكامل عميلًا مستقلًا عبر `POST /api/v1/integrations/clients` ويحدد أقل نطاقات لازمة. يعيد الخادم `clientId` و`clientSecret` مرة واحدة؛ خزّن السر في مدير أسرار النظام المتصل ولا تحفظه في المستودع. يرسل النظام الاعتماد إلى `POST /api/v1/integrations/token` للحصول على رمز Bearer صالح لساعة واحدة، ثم يرسله في `Authorization: Bearer …`. التحقق من السر والرموز ونطاقات ربط المعرّفات وطلب البحث المصرح به يعمل من قاعدة البيانات، وتسجل عمليات التكامل في سجل التدقيق باسم العميل المصدر.

النطاقات المتاحة حاليًا هي `identity-map:read` و`identity-map:write` و`patients:lookup`. يمنح نطاق البحث الوصول إلى نتيجة البحث برقم الهوية، بما يشمل البيانات الأساسية وآخر زيارة، لذا يجب منحه فقط لنظام يحتاج هذه البيانات فعلًا. إصدار الرموز لا يتيح تلقائيًا كل موارد النظام؛ لكل مسار تفويض مستقل.

## ضوابط مهمة قبل ربط الإنتاج

- استخدم HTTPS، وعميلًا منفصلًا لكل نظام، وأقل نطاقات ممكنة.
- اتفق على مصدر الحقيقة لكل حقل، وسياسة التعارض، والحذف/الإلغاء، ومعالجة إعادة المحاولة.
- لا ترسل رقم الهوية أو بيانات صحية في سجلات التطبيقات أو عناوين URL أو معرف الطلب.
- تحكم في صلاحيات العيادات على الخادم. إخفاء عنصر في الواجهة لا يمثل تفويضًا.
- راجع عقد OpenAPI وسياسة التعارض وإعادة المحاولة وملكية الحقول قبل أي مزامنة تشغيلية واسعة.
